# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Transcriber: a local-first, single-user desktop app that turns dropped meeting recordings into transcripts (faster-whisper large-v3, CUDA-first) plus an LLM-generated summary (which carries the notable facts and the action items as sections), filed into a per-project meetings vault. (Separate facts and action-items extractions existed once; both were retired in favour of the summary, and legacy `facts/`, `action items/` and `exports/` trees stay on disk unread.) **Everything runs locally — no cloud LLM, no cloud STT, no external integrations, ever.** KISS/YAGNI; Windows is the primary platform (macOS installer exists but is less tested).

## Monorepo layout — three payloads

| Path | Payload | Toolchain |
|---|---|---|
| `apps/desktop/` | Tauri 2 + React UI; `src-tauri/` is the Rust shell | npm + cargo |
| `services/transcription/` | Python transcription/LLM service (FastAPI + CLI) | `uv` only — never system `python` |
| `crates/vault/` | Rust library: vault naming/routing rules | cargo |

Supporting: `installer/` (NSIS hooks), `scripts/` (bootstrap, build, version sync — has its own pytest suite in `scripts/tests/`), `docs/` (setup, config contract, releasing, smoke checklists), `specs/` (per-feature spec/plan/verification documents — the design history).

Local-only, not part of the build: `vexa/` (gitignored reference repo), `local/` (zips), `crates/whisper-sys` (empty untracked leftover of the paused Rust-only migration — main still ships the Python service).

## Commands

QA fans out across all three payloads via the root `Makefile` (`make` exists only after `scripts/bootstrap.ps1` has run once; every target's direct equivalents are commented in the Makefile):

```
make format   # cargo fmt --all | prettier | ruff format
make lint     # clippy -D warnings | eslint | ruff check | sync_version --check | verify_locks --check | gen_diarization_runtime --check
make type     # cargo check | tsc --noEmit | mypy src
make test     # cargo test --workspace | vitest | pytest | pytest scripts/tests
```

PowerShell 5.1 has no `&&` — run chained commands one at a time.

Single tests:

- Python: `uv run --directory services/transcription pytest tests/test_llm_units.py -q` (add `-k name` to narrow). The default run is model-free, GPU-free and network-free (<30 s); the opt-in GPU integration test is `uv run pytest -m gpu` from `services/transcription/` and self-skips without a configured sample.
- Rust: `cargo test -p vault <name>` / `cargo test -p transcriber-desktop <name>` (workspace members are `vault` and `transcriber-desktop`)
- TS: `npm --prefix apps/desktop run test -- src/App.test.tsx`
- Build scripts: `uv run --with pytest -- pytest scripts/tests -q`

Dev inner loop (spawns the Python sidecar automatically; app opens even if the sidecar never gets ready):

```
cd apps/desktop && npm run tauri dev
```

Installer build: `make installer` → `dist/Transcriber_<version>_x64-setup.exe` (+ `.sha256`, `build-manifest.json`). It bakes a relocatable CPython into `apps/desktop/src-tauri/resources/pyenv/` and runs `tauri build -- --locked`. The bake is CPU-only by design — the CUDA runtime (~1.4 GB of `nvidia-*-cu12` wheels) is downloaded at first run into the install dir's `runtime\`, because 32-bit `makensis` cannot compile the CUDA-baked payload.

## Architecture

**App ↔ service split.** The Tauri Rust shell (`apps/desktop/src-tauri/src/`) spawns `services/transcription` as a localhost-HTTP sidecar (`sidecar.rs`) and talks to it from React via Tauri commands (`commands/`). A dropped recording runs the drop-to-insights chain automatically: transcribe → summarize → export → compress, chained app-side in `jobs.rs` (the service refuses a derived job until `transcript.json` exists, so stages submit as their predecessor lands `Done`). The summarize and export stages are skipped when no LLM model is installed (the compress stage then follows the transcription directly), the chain advances only off a successful stage, and it never fires for a manual re-transcribe, summarize or export. The export (`export.md` + a share-named PDF) lands in the meeting folder itself under stable names, overwritten on re-export. The compress stage (`compress.py`, a `compress` job) re-encodes a **video** `source.<ext>` to a smaller HEVC `source.mp4` (`hvc1`-tagged) in its place — in-process through PyAV's bundled FFmpeg, never an external binary; x265 CRF 26 with the shorter side capped at 1080p, and deliberately no NVENC path (measured on the operator's 4K screen recordings: same-resolution H.264 re-encodes do not shrink them, and at 1080p x265 was a third of x264's size and 2.5x smaller than NVENC HEVC at the same speed) — verified before the swap and skipped with a warning for audio-only or already-small recordings; it is gated app-side by the app-only `compress_video` key (absent = on, Settings → Recordings, no sidecar restart) and by the vault's `media::is_video_extension`. The service does all ML work: transcription (faster-whisper), diarization (optional pyannote extra), LLM summarization (bundled llama.cpp), PDF/report export. Outside the chain, the recording page's "Suggest title from summary" runs a `suggest_title` job (operator-triggered only, never chained): the LLM reads `summary.md` and its answer, sanitized in `llm/title.py` (no `-`, nothing Windows refuses in a file name, ≤ 80 chars), is the job's result manifest `{"title": ...}` — nothing is written or renamed by the service; `jobs.rs` reads it onto the finished snapshot (`suggested_title`) and the UI prefills the existing rename form with it, so a meeting is only ever renamed by the operator saving that form (`update_vault_entry`). `config.json`'s `service.base_url` set to a URL means "connect, don't spawn" — the dev/ops mode for running the service by hand. The Python package is deliberately self-contained: it imports nothing from the rest of the repo and QAs standalone.

**Sidecar handshake (ready-line contract).** `serve` prints exactly **one** JSON line to stdout for the whole process lifetime — `{"event": "listening", "port": ..., "token": ..., "pid": ...}` — after the socket is bound; every other log line goes to stderr as JSON. The Rust sidecar spawner depends on this; never add stdout prints to the service. It binds `127.0.0.1` only, with a bearer token.

**One serial worker.** All job types (transcribe, summarize, export, index) share a single serial queue — whisper, the LLM and the search embedder never infer concurrently, and with the default `llm_keep_loaded: false` the GGUF working set is released after each LLM job (the chat route deliberately keeps it loaded between turns; the embedder always unloads after an index pass). Search queries and chat completions also run through this queue (`run_serial`). Degradation over failure is the pattern throughout: diarization failures, PDF render errors, a missing embedding model or an unloadable sqlite-vec extension all record warnings and still deliver the primary artifact (text-only search included).

**Hybrid search + chat + MCP.** The service owns a rebuildable search index (`<vault_root>/.transcriber/index.sqlite3` — it travels with its vault; app-dir fallback only when no vault root is set; sqlite-vec + FTS5, bge-m3 GGUF embeddings on CPU) filled by the `index` job, which the app fires quietly after every finished job and note save. Settings offers the bge-m3 download ("Enable vector search", the `embedding_model_download` command trio); docs indexed text-only re-embed automatically on the first pass after the model lands. `POST /v1/search` fuses vector/BM25/exact-title/trigram channels with weighted RRF; `POST /v1/chat` streams a RAG answer (SSE) that the Rust shell forwards to React over a `tauri::ipc::Channel`. `transcriber-mcp` (a console script in the Python package) is a standalone stdio MCP server over the same vault+index for Claude Desktop — works with the app closed. Per-meeting `note.md` (edited in the app) sits on top. The chat lives as the library's third tab (redesign turn 9 — there are no project pages): project selector in the tab, an index-status chip/panel backed by `GET /v1/index/status`, and conversations persisted as JSON in the vault's reserved `<PROJECT>/chats/` directory (list/read/save/rename/delete via `commands/chats.rs`; sources stored by vault-relative dir, resolved to entry ids on read). `speakers.json` names feed project-level suggestions (in open mode — see the project roster below), and diarization stores per-speaker voice embeddings in `transcript.json`; after a diarized transcription, cross-meeting speaker recognition (`speaker_matching.py`, threshold `speaker_match_threshold`) pre-names voices already named in other meetings of the vault (the voice memory paragraph below) — additive only, operator assignments always win. Decode languages: ru/en/tr (constrained auto-detect).

**Speaker identification: the runtime is a first-run payload, the models are baked.** The installer never ships pyannote/torch; Settings' Speakers row fetches (1) the runtime — every wheel the `diarization` extra adds on top of the baked env, with torch/torchaudio swapped for their `cu126` CUDA builds (~3 GB; torch 2.8, the last series with the torchaudio API pyannote 3 needs), pinned in `diarization_runtime_packages.py`, which `scripts/gen_diarization_runtime.py` generates from `uv.lock` (`make lint` checks the drift) — into `<app_dir>/runtime/diarization/` (put on `sys.path` by `diarizer.py`), while (2) the three pinned pyannote snapshots (~32 MB) are **committed** under `apps/desktop/src-tauri/resources/models/diarization/` and bundled to `<install dir>\models\diarization\` — no build or release needs a Hugging Face token; `build_installer.py`'s `diarization_models_check` stage fails the build if the committed tree drifts from the revisions pinned in `diarization_runtime.py` (re-pin = change the pins, refresh once with `download-diarization-models --out` and a token, commit both). The in-app token box (`hf_token`, typed in `config.rs` alongside `diarize`, both written by `set_diarization_settings`, which restarts the sidecar) only appears on a build without them. Once fetched, the pipeline loads offline (`refs/main` pinned, hub forced offline for the load). NVIDIA GPU only. The voice memory is the meetings themselves (see the voice memory paragraph below) — there is deliberately no `<PROJECT>/speakers.json`; the `diarize` job (`commands/speakers.rs`, "Identify speakers" per meeting, or the vault-wide "Identify speakers in labelled meetings" backfill) attaches labels + embeddings to an existing `transcript.json` with ids untouched, so hand-made `speakers.json` labels become recognizable voices. A transcript being _created_ with diarization on is additionally cut at changes of voice (`split_segments_at_turns`). **Project speaker roster.** `<vault root>/<PROJECT>/roster.json` (`{schema_version, mode, names}`, `vault::ROSTER_FILE_NAME`, read/written by `commands/roster.rs`) is a _names-only_ roster with a mode: `open` keeps today's free-text box with the sibling names as a datalist, `roster` turns both name controls (`SpeakerNameField` inside `SpeakerTag` and `SelectionSpeakerMenu`) into a strict pick-list over those names. It is edited per project from the recording page's "Project speakers" panel and seeded manually only ("Add names already used in this project"); names are normalized identically in Rust and in `lib/roster.ts`. It holds no embeddings and no segment ids, so the "there is deliberately no `<PROJECT>/speakers.json`" decision stands — the voice memory is still read from the meetings, the MCP server knows nothing about the roster, and every project-level walker already skips it because it is a file, not a directory. The service reads exactly one thing from it: the names, to bound a voice memory that spans projects (below). In `roster` mode the roster additionally bounds the diarization: at submit time `jobs.rs` resolves the meeting's project through `commands/roster.rs::roster_speaker_cap` and sends `max_speakers` = roster size plus a lower `speaker_match_threshold` (from the app-only `speaker_match_threshold_strict` key — `config.rs::strict_speaker_match_threshold`, `0.4` on an untouched install) on the transcribe, re-transcribe and `diarize` submissions of that project's meetings; those two numbers are all the app sends — the roster's names the service reads from the file itself. Anything that still comes back as a generic `Speaker N` is read by the UI as an unattributed voice ("Unnamed voice", `lib/turns.ts::isGenericSpeakerLabel`) and the service mirrors the same form (`speaker_matching._is_generic`) so a generic label never becomes a named voiceprint for cross-meeting recognition.

**Voice memory: vault-wide, derived, self-invalidating.** Recognizing a returning voice (`speaker_matching.py`) reads every meeting's `speakers.json` names joined to its stored embeddings — across the whole vault, because a person is the same person in every project. Per project a name is _at home_ (heard in the project's own meetings, or listed on its roster in either mode) and matched at the job's threshold, or a _newcomer_ that needs similarity 0.8 on a voice with at least 10 s of speech; a project whose roster is in `roster` mode is offered the roster's names only. What counts as a reference is deliberately narrow (`assess_exemplars`): a sample is set aside when it is `unconfirmed` (named by the service itself — every name it writes is recorded in `speakers.json`'s `auto` map, which the app carries across saves in `write_speaker_labels` and drops on `confirm_speaker_names`; a segment is machine-named exactly while `auto[id] == assignments[id]`, and a file without the key is all the operator's), `partial` (the name covers at most half of the voice's segments), `short` (under 10 s of speech) or a `conflict` (it sounds like another person's usual voice). On top of the one-name-per-voice match, segments of 2 s or more are embedded individually (`PyannoteDiarizer.embed_spans`) and named for whoever they sound like when three or more segments of one diarized voice agree (`identify_segments`) — that is what repairs a voice the diarizer merged two people into. `voice_index.py` caches the samples in `<vault_root>/.transcriber/voices.sqlite3`; it is never invalidated by events — every read stats each meeting's two files and re-reads the ones that changed — and `GET /v1/voices/status` (the recording page's "Voice memory" section under Project speakers, `VoiceMemoryPanel`) shows who is known, from which projects, what each meeting contributes and why a sample is set aside, plus which meetings that very read had to re-read. The thresholds are measured on the operator's vault (79% → 88% segment agreement with the operator's labels at the same number of wrong names); do not loosen them without re-measuring.

**Speakers database (service side).** `<vault root>/people.json` (`people.py`) is the one thing about speakers that is authoritative rather than derived: per person a canonical `name`, `aliases` and a `bio`. It is a layer of _resolution_ over the names already written in `speakers.json` files, which are never rewritten: every spelling resolves to the person's canonical name (`PeopleResolver`; unregistered spellings fold by trimmed lower-case) before voices are compared, so a person's samples pool across spellings and projects, a roster entry stands for the person under any of their names, and a recognized voice is written under the canonical name. A rename keeps the replaced name as an alias (whatever alias list came with it); an alias that is another registered person's name merges that person in. There are no ids, so two different people cannot share a name. `people_view.py` derives the table and the person page per request from the voice index, which (schema 2) also stores per meeting how much each written name carries, for undiarized meetings too; `api/people_routes.py` serves `GET /v1/people`, `GET /v1/people/detail`, `PUT` and `DELETE /v1/people`, none of which runs a model.

**Speakers database (app side).** The library's second tab, Speakers (`SpeakersTable`, composed into `VaultPanel`'s `speakersTab` slot; sorting and filtering in `lib/speakerSort.ts`), lists every person the service knows — registered in `<vault root>/people.json` or only named in meeting labels — and a row opens the full-window `SpeakerPage`: rename, "also known as" aliases, bio, projects, voice-memory totals and the person's hand-labelled segments per meeting. A person has **no id**: every command (`commands/people.rs` — `list_speakers`, `speaker_detail`, `save_speaker`, `delete_speaker`) addresses them by any of their names, and the page stays open across a rename because `save_speaker` answers the canonical name (`onRenamed`). The commands are proxies over the service's `/v1/people` routes (trait methods `list_people` / `person_detail` / `save_person` / `delete_person`; the list and leaf types are pass-through serde structs like `VoiceStatus`); the one thing the shell adds is the id-not-path rule — `speaker_detail` swaps each meeting's `meeting_dir` for a vault entry id through `search::resolve_hit_dir` (listing the vault first when nothing is listed yet), and a meeting that resolves to nothing keeps `entry_id: null` and renders without a link rather than being dropped. A service `400` surfaces as `invalid_argument` with the service's own sentence. Nothing here rewrites a meeting's labels. App.tsx owns the navigation (`openSpeaker` under `openEntryId`, so Back from a recording opened from a speaker returns to the speaker) and the library's tab, which is why `VaultPanel`'s tab is optionally controlled. The project roster editor (`ProjectRosterPanel`'s `databaseNames`, loaded by `RecordingPage` each time the panel opens) offers the database's canonical names that are not on the roster yet — how a person known in one project joins another's roster under the same spelling.

**Service config layering** (lowest to highest): built-in defaults < `config.json` < `TRANSCRIBER_*` env vars < CLI flags. Full key table in `services/transcription/README.md`. Secrets (`token`, `hf_token`) never travel via argv and never appear in `/health` output.

**Shared config file.** App and service share `%APPDATA%\com.transcriber.desktop\config.json` (schema in `docs/config-contract.md` — the code in `config.rs` is the contract's authority). Key mechanism: the Rust `Settings` structs `#[serde(flatten)]` unknown keys at every level, so the Python service reads service-only flat keys (`diarize`, `llm_model`, `llm_ctx`, `llm_gpu_layers`, …) from the same file without the app schema knowing them.

**LLM catalog.** `services/transcription/src/transcription/llm_catalog.py` pins exactly one GGUF model: Qwen3.5-9B (fits a 12 GB GPU fully). There is deliberately no model switching (the old 35B option and the `select_llm_model` command were removed); config load migrates a retired `llm_model` id to the default, and the hand-picked-GGUF escape hatch (`llm_model_file` etc.) still wins over the catalog. `llama-cpp-python` ships as two mutually exclusive uv extras of the same pinned version — `llm-cpu` (what the installer bakes) and `llm-cuda`; because the wheels share name+version, switching by hand needs `uv sync --extra llm-cuda --reinstall-package llama-cpp-python` once. `llm_gpu_layers: -1` auto-fits whole layers to free VRAM via NVML.

**Whisper weights are a prerequisite, not the service's job.** The local provider always loads with `local_files_only=True` and never downloads weights; a missing `large-v3` snapshot under `model_path` fails every job with `error_kind="model_load"`. Model/CUDA-runtime downloads happen through the app's first-run wizard and download endpoints, not inside the provider.

**Vault rules live in Rust.** `crates/vault` owns naming/routing of recordings and artifacts into the meetings vault; the app consumes it. A dropped recording is named `<PRJ> - <YYMMDD> - <Name>[ - <Type>]` — `-` is reserved as the section separator (spaces around it optional, spaces inside a section kept), so a name that splits into five or more sections goes to `unsorted/` verbatim, three sections file an untyped meeting and four carry the optional meeting **type**. The type persists as the meeting folder's own third section (`<YYMMDD> - <Name>[ - <Type>]`), is parsed back out of it for display, and is edited from the recording page's rename form (which refuses a `-` in either the name or the type). Don't reimplement path logic elsewhere.

**Version.** `version.txt` is the single source of truth. Never hand-edit versions in the five manifests or `Cargo.lock` — use `uv run scripts/sync_version.py --set X.Y.Z`; `--check` (run by `make lint`) fails on drift.

## Releasing — commit subjects are load-bearing

Merging to `main` **is** the ship decision (no release PRs). `tag.yml` computes the next version from conventional-commit subjects since the last `v*` tag: `feat:` → minor, `fix:`/`perf:` → patch, `feat!:`/`BREAKING CHANGE:` → major, everything else → no release. CI then commits the bump + CHANGELOG to `main`, tags `vX.Y.Z`, and `release.yml` builds both installers (Windows NSIS + macOS dmg) and publishes one GitHub Release. A failed build leaves a tag with no release — re-run `release.yml` on the tag, it's idempotent. Details in `docs/releasing.md`.
