# Blueprint: Strict roster mode bounds speaker identification and hides unmatched voices

## Summary

When a project's roster is in `roster` mode ("use only the names from the project roster"), re-running speaker identification must not surface new people, yet today it still yields `Speaker 7`-style labels. Root cause: the roster (`<PROJECT>/roster.json`, shipped in v0.23.0) is UI-only. pyannote picks its own cluster count, `speaker_matching.auto_assign_speakers` names only clusters whose voice matches a voice already *named* in a sibling meeting (cosine ≥ `speaker_match_threshold`, default `0.5`), and everything else stays `Speaker N`, which the UI then shows as an off-roster selected option. The service already honours global `diarization_min_speakers` / `diarization_max_speakers` config keys but nothing sets them per job.

This feature (1) adds optional per-job `min_speakers` / `max_speakers` **and a per-job `speaker_match_threshold`** to the service's job submit contract, (2) has the Rust shell fill `max_speakers` from the meeting's project roster at submit time (strict mode with N names → `max_speakers = N`; anything else → unchanged) **and, on those same submissions, a lower matching threshold** (`speaker_match_threshold_strict`, a new `config.json` key, default `0.4`) so a cluster that is *nearly* a known voice gets its roster name instead of a generic label, for the transcribe stage of the drop chain, re-transcribe, and the standalone `diarize` job (per-meeting "Identify speakers" and the vault-wide backfill), and (3) makes the transcript view, in roster mode, read any generic `Speaker N` label that *still* remains as an *unattributed* voice: the roster pick-list with a placeholder, turn boundaries intact, nothing invented. The service stays roster-agnostic: it receives numbers, never names.

## Requirements

- **FR-1** (must): The service accepts optional per-job speaker bounds on `POST /v1/jobs` and applies them to that job's diarization pass only, overriding the global `diarization_min_speakers` / `diarization_max_speakers` config keys. The service knows nothing about rosters — it receives integers.
  - [ ] `JobCreate` (`schema.py`) accepts `min_speakers` and `max_speakers` as optional integers ≥ 1 on `transcribe` and `diarize` jobs; both absent ⇒ behaviour byte-for-byte as today (config bounds apply).
  - [ ] A per-job bound overrides the corresponding config key for that job; the *other* bound, when not given, still falls back to its config value independently (e.g. config `min=2,max=6` + job `max=3` ⇒ pipeline gets `min_speakers=2, max_speakers=3`).
  - [ ] The pyannote pipeline is invoked with exactly the effective bounds as keyword arguments (`min_speakers` / `max_speakers` present only when an effective value exists) — on both the `return_embeddings=True` call and its `TypeError` retry.
  - [ ] Both diarization entry points honour the bounds: a `transcribe` job with `diarize` on (`JobManager._diarize_segments`) and the standalone `diarize` job (`_diarize_existing_sync`).
  - [ ] Invalid requests are rejected with 422 and leave no ledger row: `max_speakers: 0`, `min_speakers > max_speakers`, or either bound on a `summarize` / `export` / `index` job.
  - [ ] A diarizer that receives no bounds is called exactly as today (the bounds kwargs are omitted, not passed as `None`), so existing engines and fakes keep working.

- **FR-2** (must): The Rust shell fills `max_speakers` from the meeting's project roster at submit time, for every job that runs the diarization pass.
  - [ ] A `transcribe` submission for a meeting filed under `<root>/<PROJECT>/` whose `roster.json` has `mode: "roster"` and N ≥ 1 normalized names carries `"max_speakers": N` on the wire; no `min_speakers` is sent.
  - [ ] No bound is sent (the key is absent and the JSON body is byte-identical to today's) when the meeting is under `unsorted`, the roster is `open` mode, the roster file is missing/unreadable, or the strict roster has zero names.
  - [ ] The same rule applies to the `diarize` job submitted by "Identify speakers" (`diarize_vault_entry`) and by the backfill (`diarize_labelled_meetings`): the `job_type: "diarize"` body carries `max_speakers` under the same conditions.
  - [ ] The drop chain's derived stages (`summarize`, `export`) and the `index` job never carry bounds; their bodies are unchanged.
  - [ ] Re-transcribe of a filed recording (`enqueue_filed`) resolves the roster the same way as a fresh drop (both pass through the registry's single submit point).
  - [ ] The roster is read when the job is *submitted* to the service, not when it is enqueued — a backfill of many meetings sees roster edits made while earlier jobs were running.

- **FR-3** (must): In roster mode, a generic diarization label is never shown as a person. The transcript keeps the raw label for turn grouping; the UI withholds it.
  - [ ] With a roster in `roster` mode, a turn whose label matches the service's generic form (`Speaker <digits>`, `SPEAKER_LABEL_PREFIX` in `diarization.py`) renders its tag as an unattributed voice — placeholder text "Unnamed voice" (unassigned styling), never the literal `Speaker N`.
  - [ ] Opening that tag shows the roster pick-list on its "Choose a name…" placeholder with only roster names; no off-roster `Speaker N` option is listed.
  - [ ] Turn boundaries are identical to open mode for the same transcript: two adjacent generic clusters (`Speaker 1` then `Speaker 2`) remain two turns (grouping keys on the raw label, not the display name).
  - [ ] Choosing a roster name for an unattributed voice that holds several turns offers the scope choice "Only this turn" / "All N turns of this voice"; "All …" relabels every segment carrying that raw label (the existing rename-everywhere path).
  - [ ] The reuse buttons beside a tag and the selection popover's known-names list exclude generic labels in roster mode.
  - [ ] A roster name already on a turn (hand-assigned or pre-named by voice memory, e.g. "Anna") still shows as that name; open mode and unfiled recordings are unchanged (`Speaker N` shows as before).

- **FR-4** (should): A generic label never counts as a *named* voice for cross-meeting recognition. Today a sibling's `speakers.json` can carry `Speaker 2` for untouched segments (the viewer saves the whole map, seeds included), and `collect_project_voiceprints` would then "recognize" a new cluster as `Speaker 2`.
  - [ ] `collect_project_voiceprints` ignores assignments whose name matches the generic form; a sibling whose `speakers.json` names a label only generically contributes no voiceprint.
  - [ ] A sibling naming a voice "Anna" still pre-names a matching cluster (existing behaviour preserved).

- **FR-5** (should): Docs describe the new behaviour.
  - [ ] `services/transcription/README.md`: the config-key table rows for `diarization_min_speakers` / `diarization_max_speakers` and `speaker_match_threshold` note the per-job override; the `POST /v1/jobs` sections for `transcribe` and `diarize` document `min_speakers` / `max_speakers` / `speaker_match_threshold` and the 422 rules.
  - [ ] `docs/config-contract.md`: `speaker_match_threshold_strict` is documented as a typed top-level key beside `diarize` / `hf_token` (type, default, derivation, who reads it — the app, not the service).
  - [ ] `docs/setup.md` "Project speaker roster" paragraph: strict mode caps speaker identification at the roster size, matches known voices a little more leniently, and shows whatever still does not match as "Unnamed voice"; first naming of a new person is still manual.
  - [ ] `CLAUDE.md` "Project speaker roster" paragraph: the service is still roster-agnostic but now receives `max_speakers` and `speaker_match_threshold` from the shell; the UI treats generic labels as unattributed in roster mode.

- **FR-6** (must): The service accepts an optional per-job `speaker_match_threshold` on `POST /v1/jobs` that overrides `config.speaker_match_threshold` for that job's cross-meeting speaker recognition. Numbers only — the service never learns *why* a caller lowered it.
  - [ ] `JobCreate` accepts `speaker_match_threshold` as an optional float with `0.0 ≤ value ≤ 1.0` on `transcribe` and `diarize` jobs; absent ⇒ `auto_assign_speakers` runs with `config.speaker_match_threshold` exactly as today.
  - [ ] When given, that value is what `auto_assign_speakers` receives as `threshold=` in **both** naming paths of `jobs.py`: after a diarized `transcribe` (`_diarize_segments` → the "naming speakers" phase) and inside the standalone `diarize` job (`_diarize_existing_sync`).
  - [ ] Observable effect: a sibling voice named "Anna" at cosine `0.45` to a new cluster is *not* pre-named under the default `0.5`, and *is* pre-named when the job carries `speaker_match_threshold: 0.4`.
  - [ ] Invalid requests are rejected with 422 and leave no ledger row: `1.5`, `-0.1`, or the field on a `summarize` / `export` / `index` job (the same rule as the bounds).
  - [ ] `GET /v1/jobs/{id}` (`JobStatus`) echoes none of the request's tuning fields today (`diarize`, `language`, … are not returned), so neither the bounds nor the threshold are echoed — the response schema is unchanged.

- **FR-7** (must): In strict roster mode the Rust shell sends a lower matching threshold alongside the speaker cap, read from a new shared-config key it owns.
  - [ ] `config.json` gains an optional top-level `speaker_match_threshold_strict` (number in `[0, 1]`), typed in `config.rs`'s `Settings` as `Option<f64>`; absent by default, never written as `null`, and preserved across every load → modify → save round-trip (`set_diarization`, `set_meetings_root`).
  - [ ] The effective strict threshold (`config::strict_speaker_match_threshold(&Settings) -> f64`) is the key's value when set and finite within `[0, 1]`; otherwise `max(0.2, base − 0.1)` where `base` is the flat `speaker_match_threshold` in the same file when it is a finite number (the service reads that key from `extra`), else the service default `0.5`. So an untouched `config.json` yields `0.4`; a config with `speaker_match_threshold: 0.35` yields `0.25`; `0.25` yields the floor `0.2`; an out-of-range strict key is ignored, not an error.
  - [ ] Every submission that carries `max_speakers` (FR-2: strict roster with N ≥ 1 names — `transcribe`, re-transcribe, and `diarize`) also carries `"speaker_match_threshold": <effective strict value>`; every submission that carries no `max_speakers` carries no threshold either (body byte-identical to today's).
  - [ ] The value is resolved from the settings the app loaded at startup (`AppState::new_with` hands it to the `JobRegistry`); editing the key by hand takes effect on the next app start, like every other flat tuning key in that file.

**Non-functional**:

- **NFR-1**: `make test` stays model-free, GPU-free and network-free: no new test imports pyannote/torch or spawns the sidecar; the engine is exercised through the existing stub pipeline (`tests/test_diarizer.py` pattern) and `FakeDiarizer`, the shell through `FakeService` / `wiremock`.

## Out of scope

- Sending `min_speakers` from the roster (a strict roster is an upper bound on who *may* speak, not a claim that everyone did — a forced minimum would manufacture phantom clusters). The wire accepts it for completeness; the shell never sets it.
- Option (b) of the gate question — best-effort assignment of the closest roster name below any threshold. Rejected with (c): a floor still exists, and what falls under it stays an unattributed voice (a).
- A Settings UI for `speaker_match_threshold_strict` or the global `diarization_*_speakers` / `speaker_match_threshold` keys — all hand-edited flat keys.
- A service-side `suppress_unmatched_labels` flag, a "strict roster" boolean on the wire, or any roster knowledge in the service / MCP server.
- Re-reading `speaker_match_threshold_strict` at submit time (the roster *is* re-read per submit; the threshold is a startup setting like the service's own keys).
- The "N speakers" count in `RecordingPage`'s meta line, the plain-text view, search/summary/export/MCP output that quotes `Speaker N` — these are text and counts, not name controls.
- Open-mode datalist suggestions still offering a generic label a sibling's `speakers.json` happens to carry (`list_project_speaker_names_handler`) — open mode is explicitly unchanged.
- Stripping seeded generic labels from `speakers.json` on save (would change the on-disk contract of a shipped feature; FR-4 neutralizes the consequence instead).

## Architecture

**Data flow (new, end to end).** `<root>/<PROJECT>/roster.json` (`mode: roster`, N names) → `commands::roster::roster_speaker_cap(root, meeting_dir) -> Option<u32>` (new; reads the file with the existing private `read_roster_file` + `normalize_names`, answers `Some(N)` only for strict mode with N ≥ 1, `None` for `unsorted`, open mode, missing/unreadable file or empty list) → `jobs.rs` fills `SubmitRequest.max_speakers` **and, iff the cap is `Some`, `SubmitRequest.speaker_match_threshold = Some(shared.strict_speaker_match_threshold)`** in `process_one` right before `service.submit(...)` (covers drop + re-transcribe: the one point that knows the final meeting folder after ingest) and the same pair on `LlmSubmitRequest` in `submit_llm_and_poll` when `request.kind == LlmJobKind::Diarize` (covers "Identify speakers" and the backfill) → `service/http.rs` `SubmitBody` / `LlmSubmitBody` gain `#[serde(skip_serializing_if = "Option::is_none")] max_speakers: Option<u32>` and `speaker_match_threshold: Option<f64>` → `schema.py::JobCreate.min_speakers / max_speakers / speaker_match_threshold` → `JobManager.submit(...)` → `JobState` → `diarizer.diarize(path, cancel=…, on_progress=…, **bounds)` where `bounds` holds only the set keys → `PyannoteDiarizer.diarize(..., min_speakers=None, max_speakers=None)` resolves per-call value ⟶ config value ⟶ omitted, and passes the result as today's `call_kwargs`; then `auto_assign_speakers(..., threshold=job.speaker_match_threshold ?? config.speaker_match_threshold)` in both naming paths.

**Where the strict threshold lives.** `config.rs` `Settings.speaker_match_threshold_strict: Option<f64>` (typed like `diarize` / `hf_token`; `#[serde(default, skip_serializing_if = "Option::is_none")]`), plus `pub const DEFAULT_STRICT_SPEAKER_MATCH_THRESHOLD: f64 = 0.4`, `pub const STRICT_SPEAKER_MATCH_THRESHOLD_FLOOR: f64 = 0.2` and the pure resolver `pub fn strict_speaker_match_threshold(settings: &Settings) -> f64` (FR-7 c2; the `base` lookup reads `settings.extra["speaker_match_threshold"]` as a number). `jobs.rs` `Shared` gains `strict_speaker_match_threshold: StdMutex<f64>` initialised to the constant, with a sync `JobRegistry::set_strict_speaker_match_threshold(f64)` — an optional setter in the `set_status_sink` idiom (`AppState::new_with` is sync), so no constructor signature changes and every existing `JobRegistry::new` / `with_poll_interval` caller (inline tests, `tests/e2e_flow.rs`, `tests/job_phase.rs`, `tests/common`) keeps compiling. `AppState::new_with` (`commands.rs`) calls the setter with `config::strict_speaker_match_threshold(&settings)` right after `set_status_sink`, which covers production (`lib.rs`) and the test harness (`build_state`) alike.

**Components touched.**

- Service: `diarizer.py` (`DiarizerProtocol` + `PyannoteDiarizer.diarize` keyword-only bounds), `schema.py` (fields + validator), `app.py` (pass-through), `jobs.py` (`submit`, `JobState`, both diarize call sites, both `auto_assign_speakers` call sites), `speaker_matching.py` (FR-4 generic-name filter in `collect_project_voiceprints`; the generic pattern is derived from `diarization.SPEAKER_LABEL_PREFIX`, one regex, one place). `auto_assign_speakers` / `match_speakers` themselves are unchanged — they already take `threshold=`.
- Shell: `config.rs` (key, constants, resolver), `service/mod.rs` (`SubmitRequest`, `LlmSubmitRequest` + `max_speakers: Option<u32>`, `speaker_match_threshold: Option<f64>`; both derives drop `Eq` — `f64` is not `Eq`, and nothing hashes them or needs more than `PartialEq`), `service/http.rs` (wire bodies + the inline tests' literals), `service/fake.rs` (inline test literal), `commands/llm.rs` and `commands/speakers.rs` (constructors set both fields `None`; the registry fills them), `commands/roster.rs` (`roster_speaker_cap`), `commands.rs` (`AppState::new_with` wiring), `jobs.rs` (the two fill points, the `Shared` field + setter; the roster read runs in `spawn_blocking` like the roster handlers). `jobs.rs` calling into `commands::roster` is a mild layering inversion, accepted over injecting a resolver into `JobRegistry` (YAGNI) — the registry is the only place that knows the meeting folder after ingest.
- UI: `lib/turns.ts` gains `isGenericSpeakerLabel(name)` (`/^Speaker \d+$/`, the service's `SPEAKER_LABEL_PREFIX` form — mirrored, documented as such) and `groupIntoTurns` is untouched (raw labels keep driving turn boundaries). `TranscriptViewer.tsx` filters `known` by the predicate when `picker.roster !== undefined`. `SpeakerTag.tsx` derives `unattributed = roster !== undefined && speaker !== null && isGenericSpeakerLabel(speaker)`: the idle button shows "Unnamed voice" with the unassigned style, the editor's draft starts at `""` (so `SpeakerNameField` lists no off-roster option), aria-label "Name this voice", scope button "All N turns of this voice"; the commit path is unchanged (`onRename(rawLabel, chosen)` still relabels every segment of that cluster). `SpeakerNameField.tsx` and `SelectionSpeakerMenu.tsx` need no change (they receive `known`/`roster` already filtered).
- Docs: `services/transcription/README.md`, `docs/config-contract.md`, `docs/setup.md`, `CLAUDE.md`.

**Schema/API changes.** `POST /v1/jobs` gains two optional integer fields (`min_speakers`, `max_speakers`, ≥ 1, `min ≤ max`) and one optional float (`speaker_match_threshold`, `0 ≤ v ≤ 1`), all `transcribe`/`diarize` only. `GET /v1/jobs/{id}` is unchanged (it echoes no request tuning fields). `config.json` gains the optional typed top-level key `speaker_match_threshold_strict` (app-read only; the service ignores it via its own flatten). `transcript.json`, `speakers.json` and `roster.json` are unchanged. No IPC command signature changes (the UI never sends bounds or thresholds; the shell derives them).

**Risks**:

- pyannote honouring `max_speakers = N` still yields up to N clusters, and any not matching a named voice at the strict threshold still surfaces as `Speaker N` in the data — mitigated by T5 (FR-3), which is the actual "never see a new person" guarantee; T1–T4 and T7 reduce how often it happens.
- A lower threshold raises the false-match rate (a new voice named as a roster member). Bounded by: the floor `0.2`, the default delta of only `0.1`, `match_speakers`' greedy one-name-per-meeting rule, "additive only — operator assignments always win", and the key being tunable per install (`speaker_match_threshold_strict`). This is why (a) stays for the remainder rather than (b). No measured data exists on this machine (diarization has never run here); the defaults are engineering judgment, logged as assumptions, and the operator's post-release smoke is the check.
- No pyannote runtime on the dev machine — the engine call is verified only against the stub pipeline in T1; the real run is the operator's post-release smoke (`docs/setup.md` flow). Called out in T6's Done when.
- Adding fields to `SubmitRequest` breaks the struct literal in `apps/desktop/src-tauri/tests/job_phase.rs`; implementers may not edit tests, so T3's test-author makes that two-line fixture edit (`max_speakers: None, speaker_match_threshold: None`) alongside writing T3's test file. No other task touches `job_phase.rs`.
- The generic-label predicate exists twice (Python `speaker_matching.py`, TS `lib/turns.ts`), both derived from `SPEAKER_LABEL_PREFIX = "Speaker "`; each site comments the mirror. Acceptable for a two-token pattern; a shared constant would need a new cross-payload contract.
- The shell derives the strict default from the flat `speaker_match_threshold` it can see in `config.json`, but the service's effective value may also come from `TRANSCRIBER_SPEAKER_MATCH_THRESHOLD` / a CLI flag, which the shell cannot see — in that (dev-only) case the strict value may not be exactly "global − 0.1". Setting `speaker_match_threshold_strict` explicitly removes the ambiguity; documented in T6.
